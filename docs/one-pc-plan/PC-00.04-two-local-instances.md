# PC-00.04 — два локальных экземпляра Akula на одном ПК

Проверено: 2026-10-24. Локальное evidence для [AKULA-ONE-PC-PLAN-01](https://app.notion.com/p/40332a84beec8199b005f7a239210763), карточка [PC-00.04](https://app.notion.com/p/40332a84beec81449ba9fd074d599aba). Статус карточки при чтении — «В очереди»; Notion, GitHub PR и remote refs не изменялись.

## Критерии локального шага

1. Два отдельных профиля, app-data-каталога и vault-пути на одном физическом ПК.
2. Две независимые P2P identity в отдельном test-only пространстве Credential Manager; EndpointId и device-id должны различаться.
3. Оба экземпляра должны запуститься, идентичности должны читаться отдельным процессом, затем временные credentials должны быть удалены и отсутствие проверено.
4. Зафиксировать границы симуляции: разные loopback-подсказки не являются активными P2P listeners или проверкой сети/второго устройства.

## Реализация

- В `aquilum-app/core/src/p2p_device_identity.rs` test-only feature выбирает `CRED_PERSIST_SESSION`; обычная identity без этой feature сохраняет прежний `CRED_PERSIST_LOCAL_MACHINE`. Test target по-прежнему ограничен `Lalalalendia/Akula/P2P/LocalHarness/`, а debug-only compile guard не позволяет включить harness в release.
- `scripts/one-pc/run_p2p_smoke.ps1` проверяет production identity compile без test feature, запускает namespace-negative test, собирает отдельный debug harness, создаёт два per-run ключа, запускает профили A/B с разными env targets и проверяет EndpointId, app-data и vault-разделение.
- `scripts/one-pc/cleanup_p2p_smoke.ps1` удаляет только targets из конкретного run summary и проверяет, что после удаления `--id` отвечает `device identity has not been initialized`.
- `scripts/one-pc/README.md` описывает scope сессии и границы smoke.

### Причина изменения persistence только для harness

Одноразовый Win32 probe в текущем изолированном logon session дал: `CRED_PERSIST_SESSION` — write/read/delete PASS; `CRED_PERSIST_LOCAL_MACHINE` — `CredWrite` отказал с Win32 `1312` (`ERROR_NO_SUCH_LOGON_SESSION`). Windows определяет session-persistent credentials как действующие в пределах logon session и невидимые другим logon sessions; см. [официальное описание `CREDENTIALW.Persist`](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw). Поэтому временные harness keys используют session scope и затем удаляются; постоянный production target не менялся.

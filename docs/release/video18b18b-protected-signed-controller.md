# VIDEO-18b-18b — подпись пяти реальных PE и защищённый OS-lock: интеграционный лабораторный контракт

**Статус: PR-only / NON-RELEASE / NO PRODUCT APPLY.** Этот этап связывает ранее принятый криптографический контракт #1000 с реальным пяти-PE Windows-стендом #998/#999 без нарушения no-growth/fanout ограничений `aquilum-app/native/src/updater/release.rs`.

## Реализация

1. Существующая отдельная библиотека `labs/video-lite/video18b18-signed-five` предоставляет наружу **только read-only тип** `SignedFive` и методы `version`, `source_commit`, `cargo_lock_sha256`, `generation_sha256`, `verify_stage`. Конструктор с подменяемым ключом компилируется **только** с feature `lab-only-signature` для Windows и дополнительно отказывает вне GitHub-hosted pull_request. Публичный пяти-EXE release gate остаётся **false**. Штатная Akula не зависит от библиотеки.
2. Новый `labs/video-lite/video18b18b-controller` — `publish=false`, отдельный Cargo workspace, зависимости на **тот же** signed-five и `chaptera-update-engine/chaptera-update-orchestrator` из точного `rar2@32a803e67244836d2794f9bbbdf9b24deab63d7e`. Отсутствующий в upstream Cargo.lock создаётся только в одноразовом лабораторном checkout и его SHA выводится в лог. Это не reviewed релизный dependency lock.
3. На настоящем GitHub-hosted Windows-2022 runner собираются пять реальных PE (Akula, Shiva, Rust mux, yt-dlp, QuickJS) с уже действующими source/pin/size проверками. Два настоящих NSIS создают GUID-only защищённый `%ProgramFiles%\AkulaVideo18bRealNsisLab-<GUID>`: пять старых EXE в корне и пять — в `current/`. Отдельная непривилегированная Windows-учётная запись подтверждает отказ изменить защищённую установку.
4. Из этих реальных PE создаётся пятый набор кандидатных файлов **только в RUNNER_TEMP**, намеренно с изменёнными хвостовыми байтами. Добавленные байты делают все пять SHA отличными от старых. **Кандидат не подписан сертификатом издателя и никогда не запускается**; его можно только байтово проверять.
5. Генерируется отдельный одноразовый Minisign-ключ. Подписывается точный JSON manifest: version `0.3.21`, GitHub PR HEAD, существующий `aquilum-app/Cargo.lock` SHA, точные имена, размеры и SHA всех пяти кандидатов. Проверка подписи проводится независимо самим Minisign CLI. Приватные ключи остаются на эфемерном runner и удаляются.
6. Один внешний тестовый Rust-процесс (расположенный вне `current/`) валидирует строго GUID-only защищённый root, staging в соответствующем RUNNER_TEMP, отсутствие Windows reparse/junction и подлинную подпись **до** разбора содержимого и до записи журнала. Проверяются плохая подпись/ключ, downgrade, изменение манифеста, SHA файла с изменением того же размера и лишний PE — все должны отказать **без журнала транзакции**.
7. После успешной подписи и byte-level приёмки тот же процесс захватывает реальный `rar2::InstallLock`, запрещает второму владельцу lock, переносит кандидата через `UpdateEngine::begin_verified_candidate`, повторно сверяет подписанные пять staged файлов после копирования, проводит retain + activate и сверяет все пять PE в `current/` с точным signed manifest. Плоский резервный набор остаётся без изменений.
8. Поскольку настоящая GUI Akula нового поколения **не запускалась** и первый реально представленный кадр с generation-bound ACK отсутствует, `confirm_candidate` **не вызывается**. Новый экземпляр `UpdateEngine` обязан откатить все пять исходных PE до прежнего SHA. После разблокировки/очистки только лабораторных файлов штатный NSIS должен удалить защищённый каталог, сохранив отдельные локальные заметку и медиа.
9. Source/negative CI проверяет все перечисленные границы и не допускает публикации .exe/.key/.minisig или переключения channel. `aquilum-app/native`, штатный двухкомпонентный updater, рабочие установки, синхронизация, VPS и продуктивные миграции **не изменены**.

# VIDEO-18b-17 — реальная защищённая пяти-PE генерация с OS-lock и журналом rar2

**NON-RELEASE / одноразовая GitHub-hosted Windows-2022 PR лаборатория.** На исходном продукте не меняются signed updater, NSIS поставка, пользовательские файлы и публичный канал.

## Контекст

VIDEO-18b-16 (#998) принят: NSIS может сохранить защищённый плоский набор старых пяти настоящих EXE и подготовить рядом `current/` с полным вторым набором, сохранив исправный dual-layout uninstall. Но до этого теста `rar2` был проверен только на синтетических PE-маркерах в `Temp` (#997). Следующий шаг — проверить работу **на реальных пяти PE внутри защищённого Program Files**, не называя это рабочим подписанным updater.

## Проводимая проверка

1. Windows PR CI собирает те же пять реальных PE из исходных зафиксированных версий, проверяет source SHA/размеры, ставит первый и второй **настоящие NSIS** в `%ProgramFiles%\AkulaVideo18bRealNsisLab-<GUID>`; `current/` содержит пять реальных EXE, прежние корневые пять остаются рабочими.
2. Загружается строго `Lalalalendia/rar2@32a803e67244836d2794f9bbbdf9b24deab63d7e` в одноразовую директорию CI. В pinned `chaptera-update-orchestrator/tests` копируется отдельный Akula-тест. Upstream `rar2` не переписывается; он запускается именно со своими `InstallLock` и `UpdateEngine`.
3. Процесс проверяет, что root — ровно **новый GUID-каталог непосредственно в Program Files**, `stage` — точный GUID-каталог в RUNNER_TEMP, оба не symlink/junction, внутри текущей генерации строго пять правильных MZ PE с длиной и SHA; исходные пять вне `current/` имеют идентичные хеши.
4. Для реального отличия кандидата от старой версии в **одноразовую лабораторную копию** пяти реальных PE добавляется хвостовой marker. Это преднамеренно инвалидирует подписи кандидата; такой набор **запрещено запускать, публиковать или выдавать за signed release**. Он нужен только как другое содержимое для проверки транзакционных границ.
5. Первый захват `InstallLock::try_acquire` проходит, второй должен получить `LockBusy`; после освобождения блокировку можно получить снова. Это OS-backed lock, не PID-файл.
6. `UpdateEngine` проходит три точки: `Prepared`, `PreviousRetained`, `CandidateActivated`. На этапе activation все пять файлов действительно заменяются отличающейся лабораторной генерацией; после нового экземпляра engine вызов `recover()` возвращает все пять исходных PE с точным SHA. Старые плоские запускаемые файлы должны оставаться нетронутыми на каждом шаге.
7. После восстановления очищаются только собственные известные журналы/пустые транзакционные директории, а NSIS через свою штатную лабораторную команду удаляет защищённый корень целиком. Обычный пользователь в том же сценарии ранее не смог перезаписать защищённые файлы, отдельная Markdown-заметка и медиа сохраняются.
8. Отрицательные source tests запрещают отключить lock, потерять проверку любого PE, перестать проверять activation rollback, переключить upstream на moving branch или разрешить релиз.

## Что НЕ проверяется

- **Настоящий kill дочернего процесса, отключение питания, locked PE/AV**: аварийные фазы здесь смоделированы восстановлением новым экземпляром engine в рамках одного лабораторного процесса; отдельный процесс-kill test был в #995 на синтетических файлах.
- **Никакой подписанной кандидатуры**: загруженный исходник `rar2` не содержит корневого `Cargo.lock`, поэтому исследовательский PR CI временно создаёт lock в disposable checkout и фиксирует его SHA в логе. Это **не** воспроизводимый релизный dependency graph.
- **Никакой доставки доверенного control-process и generation-bound first-presented-frame GUI ACK.** Запрещён `confirm_candidate()` для нового лабораторного PE, каждый переход обязан откатиться. Это не рабочее автообновление, подпись, live user installation или migration.
- `updater::apply.rs` и `release::channel_ready()` в Akula не тронуты. VIDEO-18 остаётся PUBLIC RELEASE HOLD. Пользовательские файлы, VPS, production migrations и лицензионный поток в текущую очередь не включены.

# Akula VIDEO-18b-18a — проверка подписанного пятикомпонентного кандидата (NON-RELEASE)

## Проблема

Принятые PR #996–999 проверили защищённый Windows GUI, установку рядом с `current/`, журнал и восстановление всех пяти реальных PE. Но действующий Windows SignedCandidate удостоверяет **один NSIS установщик для штатной двухкомпонентной Akula**, а не отдельный набор `akula-app.exe`, `shiva-pdf-preview.exe`, `akula-video-mux.exe`, `akula-yt-dlp.exe`, `akula-quickjs.exe`. Заменять один контракт другим без новой проверки нельзя.

## Реализация

Добавлен отдельный Rust-модуль `aquilum-app/native/src/updater/release/video_five_candidate.rs`. Он доступен только во внутренних тестах и experimental video Windows compilation, не подключён к штатным `release::find`, `release::channel_ready`, `handoff` и `apply`.

Только после настоящей проверки detached **Minisign** подписи исходных байтов manifest модуль разбирает строго типизированный JSON: schema=1; product=Akula; platform=windows-x86_64; purpose=protected-video-five-exe; строгая возрастающая трёхкомпонентная version; ровно 40 lowercase hex source-commit; 64 lowercase hex Cargo.lock hash; и **ровно пять** записей PE в фиксированном порядке, с точными case-sensitive именами, SHA-256 и bounded size. Все неизвестные поля/записи/дополнительные файлы запрещены.

После подписи получается private `SignedFive` без публичного конструктора из свободного JSON. Его `generation_sha256` привязан к точным подписанным байтам manifest, а `verify_stage` потоково сверяет пять файлов, не читая их целиком в RAM, с контролем MZ, размера, SHA-256, symlink и Windows reparse. Корневой путь для `verify_stage` **должен быть отдельно авторизован доверенным контроллером**; этот вызов не выдаёт прав на установку и не защищает от TOCTOU после возвращения.

**Главное:** `VIDEO_FIVE_CHANNEL_READY = false`. Production `admit()` немедленно отказывает даже при настоящей подписи. Штатный Windows двух-EXE signed channel не меняется. Этот PR не включает релизный update discovery и не создаёт доверенный updater.

## Отдельная подпись в CI

PR workflow создаёт в `RUNNER_TEMP` новый одноразовый ключ Minisign и синтетические **MZ-маркеры** пяти файлов. Настоящий Minisign CLI подписывает JSON. Rust-тест принимает подпись и проверяет пять хешей; отрицательные тесты отклоняют изменённый manifest при сохранённой подписи, неверный ключ, одинаковую/старую версию, неверный platform/product/purpose, перестановку, отсутствующий или шестой PE, изменённый байт при той же длине, неизвестные поля, неоднозначную версию, Linux symlink и лишний файл. Тестовые секреты и данные удаляются после job, никакие PE/ключи/подписанный candidate не публикуются.

## Ограничения

- Это проверка *идентичности и целостности* лабораторного кандидата с реальной одноразовой подписью, **не подписанная владельцем пяти-EXE поставка**. Синтетические MZ-маркеры не являются реальными запускаемыми PE.
- Предыдущий `rar2@32a803e67244836d2794f9bbbdf9b24deab63d7e` не имеет закреплённого релизного Cargo.lock. Нельзя считать граф зависимостей обновляющего контроллера проверенным для выпуска.
- Нет production signed publisher five-PE workflow, привилегированного отдельного контроллера, защиты root ACL внутри самого controller, атомарного switching, receipt/first-presented-frame GUI ACK, timeout и kill/power-cut доказательств.
- Продуктивные машины, пользователи, VPS, синхронизация, штатный updater, migration и публичный релиз не затрагиваются. VIDEO-18 RELEASE HOLD сохраняется.

3. Проверки kill между фазами, power-loss, AV/locked files, недоступный диск, standard-user attacks и чистая/обновляемая Windows 10/11, не снимая HOLD до полной приёмки.

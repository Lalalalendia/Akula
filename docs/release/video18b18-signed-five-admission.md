# Akula VIDEO-18b-18a — проверка подписанного пятикомпонентного кандидата (NON-RELEASE)

## Проблема

Принятые PR #996–999 проверили защищённый Windows GUI, установку рядом с `current/`, журнал и восстановление всех пяти реальных PE. Но действующий Windows SignedCandidate удостоверяет **один NSIS установщик для штатной двухкомпонентной Akula**, а не отдельный набор `akula-app.exe`, `shiva-pdf-preview.exe`, `akula-video-mux.exe`, `akula-yt-dlp.exe`, `akula-quickjs.exe`. Заменять один контракт другим без новой проверки нельзя.

## Реализация

Добавлена **самостоятельная нерелизная Rust-библиотека** `labs/video-lite/video18b18-signed-five` с закрытым типом подписанного пятикомпонентного кандидата. Прямое подключение к существующему `release.rs` запрещено no-growth/fanout политикой репозитория, поэтому этот этап отдельно подтверждает криптографический контракт без изменения штатных `release::find`, `release::channel_ready`, `handoff` и `apply`. Перед продуктовой интеграцией потребуется согласованный рефакторинг без ослабления архитектурного правила.

Только после настоящей проверки detached **Minisign** подписи исходных байтов manifest модуль разбирает строго типизированный JSON: schema=1; product=Akula; platform=windows-x86_64; purpose=protected-video-five-exe; строгая возрастающая трёхкомпонентная version; ровно 40 lowercase hex source-commit; 64 lowercase hex Cargo.lock hash; и **ровно пять** записей PE в фиксированном порядке, с точными case-sensitive именами, SHA-256 и bounded size. Все неизвестные поля/записи/дополнительные файлы запрещены.

После подписи получается crate-private `SignedFive` без публичного конструктора из свободного JSON. Его `generation_sha256` привязан к точным подписанным байтам manifest, а `verify_stage` потоково сверяет пять файлов, не читая их целиком в RAM, с контролем MZ, размера, SHA-256, symlink и Windows reparse. Корневой путь для `verify_stage` **должен быть отдельно авторизован доверенным контроллером**; этот вызов не выдаёт прав на установку и не защищает от TOCTOU после возвращения.

**Главное:** `VIDEO_FIVE_CHANNEL_READY = false`. Вызываемый внешний `admit()` в лабораторной библиотеке немедленно отказывает даже при настоящей подписи; успешное `admit_with_key()` доступно только для проверки внутри модуля. Штатный Windows двух-EXE signed channel не меняется. Этот PR не включает релизный update discovery и не создаёт доверенный updater.

## Отдельная подпись в CI

PR workflow создаёт в `RUNNER_TEMP` новый одноразовый ключ Minisign и синтетические **MZ-маркеры** пяти файлов. Настоящий Minisign CLI подписывает JSON. Rust-тест принимает подпись и проверяет пять хешей; отрицательные тесты отклоняют изменённый manifest при сохранённой подписи, неверный ключ, одинаковую/старую версию, неверный platform/product/purpose, перестановку, отсутствующий или шестой PE, изменённый байт при той же длине, неизвестные поля, неоднозначную версию, Linux symlink и лишний файл. Тестовые секреты и данные удаляются после job, никакие PE/ключи/подписанный candidate не публикуются. Изолированный crate временно генерирует `Cargo.lock` во время CI: этот граф зависимостей **не** утверждён для релиза.

## Ограничения

- Это проверка *идентичности и целостности* лабораторного кандидата с реальной одноразовой подписью, **не подписанная владельцем пяти-EXE поставка**. Синтетические MZ-маркеры не являются реальными запускаемыми PE.
- Предыдущий `rar2@32a803e67244836d2794f9bbbdf9b24deab63d7e` не имеет закреплённого релизного Cargo.lock. Нельзя считать граф зависимостей обновляющего контроллера проверенным для выпуска.
- Нет production signed publisher five-PE workflow, привилегированного отдельного контроллера, защиты root ACL внутри самого controller, атомарного switching, receipt/first-presented-frame GUI ACK, timeout и kill/power-cut доказательств.
- Продуктивные машины, пользователи, VPS, синхронизация, штатный updater, migration и публичный релиз не затрагиваются. Файл `aquilum-app/native/src/updater/release.rs` оставлен байтово идентичным `main`. VIDEO-18 RELEASE HOLD сохраняется.

## Следующий P0

1. Изолированный, подписанный, фиксированно обновляемый privileged controller под OS lock использует тип `SignedFive` и повторную проверку точных SHA непосредственно до атомарной смены `current/` (с проверкой origin/ACL/no-reparse).
2. Реальное подписанное поколение запускается из защищённого `current/`; только **первый подтверждённый UI-frame**, привязанный к `generation_sha256` и пяти байтовым идентичностям, может разрешить commit; при таймауте и ошибке откат.
3. Проверки kill между фазами, power-loss, AV/locked files, недоступный диск, standard-user attacks и чистая/обновляемая Windows 10/11, не снимая HOLD до полной приёмки.

## VIDEO-18c-02b-02a — строгая привязка first-frame ACK к подписанному поколению (NON-RELEASE)

После принятых #1002, #1003 и #1006 добавлен метод `SignedFive::verify_first_presented_frame_ack(receipt, expected_nonce, pinned_os_child_pid)`. Он работает **только** с уже криптографически допущенным `SignedFive`: ожидаемая версия поступает из проверенного manifest, а digest — из `SignedFive::generation_sha256()`, то есть SHA-256 **сырых подписанных байтов пятикомпонентного manifest**, не одного GUI EXE. Проверяется один точный `AKULA-WIN-FIRST-PRESENTED-V1` размером до 256 байт, lowercase 128-bit nonce и PID больше 1, переданный снаружи доверенным Windows-контроллером. Чужой SHA одного EXE, неверные nonce/PID/version/generation, CRLF, двойные ACK, лишний хвост, NUL, неверные поля и переполнение буфера отклоняются.

Ограничение по доверию: это read-only проверка **формата и связи данных**; она сама не проверяет Windows OS HANDLE/PID/creation identity, видимый кадр, защищённый `current/`, наличие OS-lock, deadline, ACЛ или `rar2` journal. Внешний supervisor обязан проверить эти условия **до** принятия квитанции, повторно проверять подписанные пять PE на границе активации и не путать успех этой функции с правом на `confirm_candidate`. Публичная доставка и создание ключа издателя по-прежнему запрещены. **VIDEO-18 RELEASE HOLD** сохраняется.

Успешные unit/negative/source-контракты этого метода — только подготовительная 02b-02a. Следующий интеграционный шаг 02b-02b должен обеспечить истинно исполняемый, отдельный по байтам candidate, проверку подписи и передачу `generation_sha256` от той же подтверждённой `SignedFive` в реальный GUI controller. Положительный коммит `rar2` — отдельный 02b-03.
